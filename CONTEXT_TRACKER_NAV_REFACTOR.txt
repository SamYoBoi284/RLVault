    Original standalone Reviewed Clips screen. Untouched content-wise.

What had to change to make these compile alongside the new fragments:

- SessionPagerAdapter.kt now has two constructors — one taking a Fragment (used by the
  new SessionsFragment) and one taking a FragmentActivity (used by the restored
  SessionTrackingActivity, which calls SessionPagerAdapter(this)). Both delegate to the
  matching FragmentStateAdapter superclass constructor. This is the only structural
  change needed to support both navigation paths at once.
- strings.xml: home_log_session_button, home_dev_mode_button, home_review_clips_button,
  home_reviewed_clips_button were re-added (they're only read by the restored
  activity_home.xml).

To actually roll back to the old navigation, you'd point AndroidManifest.xml's
MAIN/LAUNCHER intent-filter at .ui.home.HomeActivity instead of .ui.main.MainActivity —
everything it needs is already in the manifest and on the classpath.

============================================================
ASSUMPTIONS MADE (flag if you want these changed)
============================================================

1. Import Clip entry point: the spec removes all Home buttons but doesn't say where
   Import Clip should live afterward. Added a FAB on the Clips destination
   (ClipsFragment) that launches ImportClipActivity, since that's the most natural
   surviving screen for it. Easy to relocate or drop if you had somewhere else in mind.

2. Bottom nav icons: stock @android:drawable placeholders (ic_menu_recent_history,
   ic_menu_slideshow, ic_menu_myplaces, ic_menu_sort_by_size, ic_menu_preferences) —
   no custom icon assets existed in the repo to draw from. Purely cosmetic, swap
   whenever real iconography is ready; the menu item ids won't need to change.

3. Fragment lifecycle strategy: used show/hide (all 5 fragments created once, kept
   alive) rather than replace(), so switching tabs preserves scroll position/state —
   matches the existing app's TabLayout+ViewPager2 pattern. One side effect: onResume()
   fires for all 5 destination fragments whenever the Activity resumes (not just the
   visible one), so HomeViewModel.refresh() etc. run a bit more often than strictly
   necessary. Harmless, just slightly more DB reads on app-foreground.
